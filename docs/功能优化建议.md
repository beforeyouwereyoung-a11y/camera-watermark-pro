## 一、已经落地的优化

### 0. v3.5.0（本轮：展签版式合并进主线 + 换品牌鲁棒性）

用户把 ChatGPT 给的「摄影作品展签 / Gallery Caption」规范（19 大节 + 22 项验收标准）
转了过来，要求「严格按照规范实现，先出效果图、确认后再合并到主线」。
效果图通过后，用户还追问了一句关键的：「这一套方案，如果切换了索尼或者其他家的，
输出效果还会保持吗？」

于是本轮拆成两段：**先把版式按规范做出来**，再**用 11 家厂商的真实 EXIF 把
「换品牌还成不成立」量出来**，把量出来的缺陷一并修掉，最后才合并进主线。

| 项目 | 说明 |
| --- | --- |
| **新增 `gallery_caption` 处理器** | 「摄影作品展签」版式：纯白卡纸留白 + 照片下方一条信息栏；左上「品牌(粗) + 型号(常规)」、左下 EXIF 参数、右侧「日期 + 官方 Logo」。照片本身**不做任何处理**（不圆角 / 不投影 / 不描边 / 不裁切 / 不调色）。之所以**新开处理器**而不是改 `watermark`：规范与 `watermark` 有三条硬冲突 —— ①它是**固定比例**版式（所有尺寸 = W 的百分比），而 `watermark` 是**自适应**布局（先测量、再走降级梯子）；②规范禁止分割线，`watermark` 底栏有竖分隔条；③规范禁止对照片做任何修饰，`watermark` 的上游常挂圆角与阴影 |
| **新增 Jinja 工具三个** | `vwr()`（与 `vw()` 只差一个 `round`，见下）、`camera_brand()`、`camera_model()`。自定义函数/过滤器改为**集中登记一份**（`_CUSTOM_GLOBALS` / `_CUSTOM_FILTERS`），避免「模板能存不能跑」 |
| **修掉机型拆分：11 台里错 7 台** | 旧模板写 `exif.CameraModelName or exif.Make`，把 `Make` 当**兜底** —— 而它才是品牌的第一权威来源。`camera_brand()` 又只「取首个词」。结果 `SONY / ILCE-7M3` 渲染成品牌「ILCE-7M3」、型号「-」；富士 `X-T5`、松下 `DC-S5M2`、OM `OM-1` 同样；哈苏 `X2D 100C` → 品牌「X2D」；苹果 `iPhone 15 Pro` → 品牌「iPhone」。**修法**：品牌以 `Make` 为准并清洗法人全称（`NIKON CORPORATION`→`NIKON`、`LEICA CAMERA AG`→`LEICA`），型号取 `Model` 并**剥掉与品牌同名的前缀**；再加一层**子品牌特判**（理光映像出的 PENTAX 机身显示 `PENTAX` 而不是 `RICOH`；OM Digital Solutions 的 `OM-1` 显示 `OM SYSTEM`） |
| **修掉 Logo 匹配：2 家失配、1 家错配** | ①徕卡资产叫 `leica_logo.png`，旧规则「资产 stem 出现在 Make 里」→ `leica_logo` ∉ `leicacameraag` → **失配**；②`config/logos/` 里没有 OM SYSTEM 资产 → 失配；③宾得 Make 是 `RICOH IMAGING` → 命中 `ricoh.png`，**给宾得相机贴了理光的标**。**修法**：两侧都做规范化（只留字母数字 + 剥掉资产名尾部的 `logo`/`brand`/`mark`），并且 **`Model` 优先于 `Make`**（更具体者胜） |
| **修掉「未匹配时渲染出字符串 `'None'`」** | 模板写 `{{auto_logo()|replace('\\','/')}}`，`auto_logo()` 返回 `None` 时被 Jinja 的 `replace` 过滤器 `soft_str()` 成字符串 `'None'` —— **真值**，于是 `Image.open('None')` 每张图刷一条 WARNING。改写成 `{{ auto_logo() or '' }}` 后彻底消失（`auto_logo()` 本来返回的就是正斜杠路径，那层 `replace` 纯属多余） |
| **Logo 先裁白边** | 内置资产普遍**不是满幅**的：`canon.png` 右侧留白 8.4%、`hasselblad.png` 15.4%、`sony.png` 6.1%，而 `nikon.png` 是满幅。判据是「三通道最小值 < 250 且不透明」—— **不能只看 alpha**，因为这些 PNG 是全不透明的，白边是**画在像素里**的，alpha 全 255，只看 alpha 一点都裁不掉（这正是上一版漏掉这条的原因） |
| **Logo 容器按形态分档** | 「contain 进 `5%W` 正方形的方框」对字标类资产不成立：同一版式下尼康可见 `200×200`（占底栏高 45%）、索尼只有 `180×35`（8%），**视觉面积差 6.3 倍**。改为按裁白边后的宽高比分档：徽标类（近方形）`5%W`、字标类（细长，宽高比 ≥ 2.5）`9%W`，两类视觉重量趋近 |
| **Logo 贴边锚在「可见墨迹右边缘」** | 旧实现锚在**容器**右边缘，非正方形资产缩完在容器里居中 → 可见墨迹贴不到照片右边界（实测内缩 哈苏 28px / 苹果 19px / 佳能 14px / 宾得 11px / 索尼 10px）。改为锚可见右边缘后，**8 个品牌全部 0px**，同时新增加宽 Logo，不会与日期打架（引擎保留了「底栏内容过宽」告警兜底） |
| **模板合并进主线** | `config/templates/标准水印Pro.json` 由旧版式（圆角 + 双层阴影 + 竖分隔线）**整体替换**为展签版式。旧的冻结在 `_draft/标准水印Pro-经典.json`，只给验收脚本出对照图用 |
| **新增两个验收脚本** | `_gallery_verify.py`（规范 22 项 + 补充项 = **93 项**，含**独立重算几何**与**换品牌一致性**两条硬线）、`_gallery_brands.py`（11 家厂商真实 EXIF 量测 + 出对照图） |
| 版本号 | 3.4.0 → 3.5.0 |

**为什么品牌要以 `Make` 为准而不是 `Model`**：
`Model` 是厂商自己起的产品名，**没有统一格式** —— 佳能写 `Canon EOS R6`（带品牌）、
索尼写 `ILCE-7M3`（不带）、苹果写 `iPhone 15 Pro`（品牌是 Make 里的 `Apple`）。
而 `Make` 是 EXIF 标准字段，装的就是厂商标识，只是常写成法人全称需要清洗。
把权威来源搞反，等于让「格式最不统一的那个字段」去决定品牌。

**为什么「贴容器右边缘」不够，要贴「可见墨迹右边缘」**：
规范第八节的字面要求是「Logo 右边缘严格等于照片右边界」，旧实现**确实满足了**这个字面要求
（容器右边缘精确对齐）。但资产不是满幅的、缩完还要在容器里居中，于是**看得见的那块**缩进去了
3~28px。同一条产线里不同品牌的照片并排看，右边界参差不齐 —— 这正是「字面满足、视觉不满足」的典型案例。

### 1. v3.4.0（修掉对比模式错位 + 预览严重失真 + 界面可控性）

用户实测反馈的原文是：「点击对比之后，一个图会覆盖在另一个图上面显示，而不是完全在分割线的左右分布，
其次待处理照片与效果预览的分界线不可以左右拖动，导致想把效果预览区域放大观看，这一条路堵死了。」

| 项目 | 说明 |
| --- | --- |
| **对比模式错位（根因）** | 成片画布和原图尺寸天生不同（画框/留白/投影会把画布撑大），前端却把两张图各自 `object-fit: contain` 塞进同一个盒子 → 各自信箱化居中 → 看起来"一张盖住另一张"。另外分割线是按**整个预览舞台**算百分比的，图片居中留白后分割线也跟着错位 |
| **照片位置几何追踪（新增机制）** | 沿处理管道累积「原图内容落在最终画布中的矩形」，存进上下文键 `_photo_rect`。**只写元数据、不碰像素**，所以对成片零影响；旋转 / 自动裁边 / 拼接这类无法继续追踪的处理器会把位置标记为不可信（置 `None`），前端自动退回整幅摆放 |
| **对比模式重做** | 左侧放**真原图**并按几何信息对齐到成品中照片的准确位置（用 `cover` 摆放，带裁切的模板也能对齐）；分割线改按**图片实际渲染框**算百分比；新增 `/api/v1/preview/meta` 接口（与预览共用缓存，不重复渲染） |
| **可拖动分隔条** | 三栏之间加两条分隔条，拖动改栏宽，双击复位，聚焦后方向键可微调；宽度记进 `localStorage`，窗口变窄时按「先压预览栏、再压左栏」的顺序夹取，保证中间栏始终可用 |
| **双击全屏放大预览** | 双击预览区把预览栏铺满整个窗口看水印细节，Esc 或再次双击退出 |
| **清空按钮拆成两个** | 「清空」改名为「取消选择」（只取消勾选），新增「清空全部内容」（照片列表 + 勾选 + 预览 + 进度一起回初始态），按决策**不做二次确认** |
| **三个板块默认折叠** | 「自定义 Logo」「画幅裁切」「输出规则」默认收起，展开状态记进 `localStorage` |
| **修掉预览严重失真（既有缺陷）** | `load_for_preview()` 先把原图降到预览尺寸，但模板里的 `{{vh(3)}}` 仍按**原始 EXIF 尺寸**解释百分比，导致 6000×4000 的照片在 1400px 预览里参数偏大约 4.3 倍（照片被挤到上半部分、底栏占半张画面）。新增 `app._preview_context()`：把 EXIF 的 `ImageWidth/ImageHeight` 改写成预览画布尺寸后再跑管道 |
| **命名规则加 `{template}`** | 默认从 `{name}` 改成 `{name}_{template}`。起因：同图换模板时输出文件名完全相同，会被"已存在"判定跳过，白白以为改了模板没生效。旧值只在**仍等于原默认 `{name}`** 时自动迁移 |
| **文件名清洗** | 新增 `safe_filename_token()`，把模板名里的 `\ / : * ? " < > \|` 与控制字符替换掉，避免 `{template}` 直接进路径导致写文件失败 |
| **镜头型号截断** | 新增 Jinja2 过滤器 `lens_short`：去括号注释 → 在第一个光圈标记处截断 → 清尾部空白与连字符 → 超 26 字符加省略号。`NIKKOR Z DX 50-250mm f/4.5-6.3 VR` → `NIKKOR Z DX 50-250mm` |
| **标准水印Pro → P2 进阶** | 在原「标准水印2」基础上再进一档：双层柔阴影（大半径低透明 + 小半径高透明叠加）、圆角 `vh(1.6)`、卡片留白。定位是"超越标准水印2" |
| **画框Pro 收敛为「中」一档** | 删除 `画框Pro-细.json` / `画框Pro-粗.json`，保留并强化 `画框Pro-中.json`（新增 `outline` 描边处理器：1px 极淡描边 + 白卡圆角 + 双层阴影） |
| **`标准水印2` 消除写死的绝对像素** | `left/right/top_margin` 由固定 `100px` 改成 `{{vh(2)}}`、`shadow_radius` 由 `100` 改成 `{{vh(2.5)}}`。原来 100px 在 4000px 宽的照片上等于没留白，在预览里却占掉三成画面 —— 这正是该模板「预览 70.0% vs 成片 90.9%」对不上的根因。改完偏差降到 **0.0%** |
| **新增 `_preview_parity.py`** | 逐模板比对「预览构图」与「真实出片构图」，偏差 >5% 直接报错。模板改过之后必跑，防止再出现「小窗口里调好、出片不一样」 |
| **程序图标重做** | 极简相机轮廓 + 下方水印条，深墨蓝 `#1F3A5F` + 亮橙 `#FF7A45`。由 `_make_icon.py` 手绘生成（4× 超采样 + LANCZOS），`.ico` 从 4 档扩到 8 档（16~256），任务栏 16px 仍可辨识 |
| **默认值调整** | JPEG 质量 95 → **100**（保留下调能力）；命名规则 → `{name}_{template}` |
| 版本号 | 3.3.0 → 3.4.0 |

**为什么"对比模式错位"要用几何追踪而不是"把两张图都拉成一样大"**：
把原图强行拉伸到成片尺寸，视觉上"对齐"了但比例是错的 —— 用户拿它看细节时会被误导。
只有沿管道真实累积照片矩形，才能做到「原图按原比例、落在成片里照片的准确位置」。

**验收证据**

- `selftest.py` 9/9、`smoke_test.py` 26/26、`regress_samefolder.py` 27/27、
  `test_features.py` 125/125、`test_v340_features.py` 32/32
- `ui_verify.py` 真实 Chromium 走查 **111/111**（含对比对齐、分隔条拖动、
  折叠记忆、双击放大、清空、控制台零报错）
- `_preview_parity.py`：预览 / 成片构图比例逐模板比对，最大偏差 **0.2%**
  （`标准水印2` 从改前的 20.9% 降到 0.0%）
- 几何自洽：4 个模板追踪出的照片矩形宽高比与原图完全一致（1.4989）

### 1. v3.3.0（修掉用户实测的竖构图堆叠 + 新增 Pro 模板）

| 项目 | 说明 |
| --- | --- |
| **修掉竖构图水印堆叠** | 底栏旧实现是**固定双列、从不测量宽度**，竖构图或超长镜头型号时左右两列与中间 Logo 必然重叠。改为**先测量后排版**：不重叠直绘 → 字号小幅缩（1.0→0.85）→ 单列左对齐 + 底栏按内容加高 → 继续缩字号（下限 0.6）→ 最后才裁切。**7 个模板全部受益，模板 JSON 一行没改**，且横/方/宽三种画幅输出**逐像素与旧版一致** |
| **日期只到月日** | `标准水印` / `标准水印2` / `文件夹名+右下角参数` 的 `[:16]` → `[:10]`，输出 `2026-10-04` 而不是 `2026-10-04 11:19` |
| **新增 `标准水印Pro`** | 三级字重层次（机型粗黑 vh3.4 / 参数中灰 vh2.4 / 日期浅灰 vh2.1）、单列左对齐、右下 Logo + 细分隔条、**不放镜头型号**、日期只到月日 —— 对齐小米徕卡 / OPPO 哈苏 / vivo 蔡司的排版语言 |
| **新增 `画框Pro-细 / 中 / 粗`** | 明信片风格：照片四周留白框 + 底部白底水印区，三种框厚可选（对应小米徕卡「白边 细/中/粗」） |
| **不做的事（有意的）** | 竖构图**不做竖排旋转**。小米 / OPPO / vivo / 华为在竖构图上仍用底部横条，靠「内容精简 + 宽度自适应 + 画框」解决；旋转文字可读性差、被社媒裁切后基本报废 |
| 版本号 | 3.2.0 → 3.3.0 |

**为什么"修掉堆叠"比"新增模板"更重要**：堆叠是**正确性问题**（输出的图是坏的），
模板审美是**偏好问题**。前者必须用代码从根上解决，否则任何用户自建的模板都会踩到。

### 4. v3.1.0 针对用户实测反馈的修复

用户拿正式版跑了真实照片，反馈了两个问题，都已定位到根因并修复：

| 反馈 | 根因 | 修复 |
| --- | --- | --- |
| **拖拽文件夹提示「不支持拖拽」** | WebView2 不给网页真实路径；pywebview 的真实路径通道又要求先用它的 DOM API 注册 `drop` 监听，而原实现用的是普通 JS `addEventListener` | 在 `desktop_app.py` 用 `window.dom.get_element('#dropzone').on('drop', DOMEventHandler(...))` 注册，把 `pywebviewFullPath` 回传前端，新增 `/api/v1/drop` 解析路径 |

| （排查中发现的隐患）**目录配置依赖防抖保存** | `await saveConfig()` 不会等防抖的 POST 真正发出，`process/start` 又只读后端内存里的 config，存在时序竞态 | 目录参数随 `process/start` 请求体下发并固化进 `job.options`；目录类改动改用非防抖的 `saveConfigNow()` |
| （排查中发现的隐患）**输出路径可能逃逸** | 文件不在输入目录下时 `os.path.relpath` 返回一串 `..`，拼出的路径会跑到输出目录之外 | `resolve_output_name()` 加兜底：逃逸时平铺到输出目录下 |
| （排查中发现的隐患）**成片被二次加工** | 输出目录在输入目录内部时，扫描输入会把上一次的成片也当素材 | 扫描时排除生效后的输出目录 |

| **单文件版启动慢** | onefile 每次启动都要解包到临时目录 | 增加文件夹版（onedir）打包，两种便携形态并存 |

### 6. v3.2.0 性能优化（用户点名「11. 性能优化」）

| 优化项 | 效果 |
| --- | --- |
| **多进程批处理（绕开 GIL）** | Windows `spawn` + `ProcessPoolExecutor`。实测 6 张照片：**串行 16.09s → 并行 5.05s（约 3.2×）** |
| **输出路径与跳过判定前置到主进程** | 原来每个线程各自算输出名，多进程下会互相抢同一个目标文件。现在由主进程统一规划（含「与原图同名」拦截、批内重名拦截、跳过判定），worker 只负责干活，天然无竞争 |
| **多进程安全兜底** | 多进程只是加速手段、不是正确性前提。池子起不来 / 子进程崩了就自动回退串行，并且只补跑**没做完**的那些（靠 `task["_done"]` 标记），已完成的结果不丢 |
| **EXIF 缓存改 LRU** | 原来是「满了就整体清空」，命中率很差。改成 `OrderedDict` LRU（默认 2048 条，可配），实测**冷读 504ms → 命中 0.007ms**，快 6 万倍以上 |
| **预览先降采样再渲染** | 以前是拿 6000×4000 原图渲染完整水印管道、最后才缩成缩略图。现在先用 `ImageOps.exif_transpose` + LANCZOS 降到长边 1400 再进管道，预览延迟大幅下降 |
| **exiftool 加 `-m`** | 忽略小警告，减少不必要的元数据解析开销 |
| **放宽大图解码上限** | `Image.MAX_IMAGE_PIXELS` 提到 4 亿，避免高像素全景图被 Pillow 当「解压炸弹」拒掉 |
| **单文件 exe 的进程数收敛** | 单文件模式下每个子进程都要让 PyInstaller 重新解包一次（本程序带 WebView2/.NET，一次数秒），所以上限压到 4；文件夹版上限 8 |

### 7. v3.2.0 验收轮补掉的三个隐患

这三条不是新功能，是**自己做验收时踩出来的**，都已修复并补了回归用例。

| 隐患 | 现象 | 修法 |
| --- | --- | --- |
| **拖拽通道只挂在 `loaded` 事件上** | 用户反馈过「拖拽文件夹提示当前环境不支持拖拽」。v3.1.0 已定位到「原生通道没注册上」，但注册动作押在 `window.events.loaded` 上——实测这个事件在非交互式会话（后台任务 / 服务 / CI）里**永远不会触发**（日志证据：`Main window failed to start`），冷启动慢的机器也可能错过 | 加一条**独立线程轮询重试**（最长 60 秒，0.6 秒一次），与 `loaded` 事件互相竞争，谁先成功算谁；用锁 + 标志位保证「最多注册一次」；重试期间日志降噪；拿不到元素就超时退出并回退到「浏览」按钮。详见制作手册 8.15 |
| **Logo 上传「先写盘再验证」** | 老实现先 `save()` 落盘、再用 Pillow `verify()`，失败就 `unlink()`。在删除受限的环境（沙箱 / 企业策略 / 杀软拦截）里 `unlink` 会失败并被 `except: pass` 吞掉，用户的 `config/logos/` 里就留下一个被拒绝的坏文件 | 改成**先在内存里验、验过了才写盘**；顺手加 16 MB 上限，防止有人传几百 MB 的图把内存吃爆。详见制作手册 8.14 |
| **测试夹具跨运行复用导致假失败** | `_feature_test/data` 是跨运行复用的固定目录（不能删，见制作手册 8.12），Logo 用例却写死了文件名，第二次跑就会撞上「同名不覆盖」逻辑而假红 | Logo 用例的名字带上 `RUN_ID`，每次运行都是全新名字，断言可复现 |

> 这三条有个共同点：**都不是功能没写对，而是「在别人的环境里会失效」。**
> 自动化验收能覆盖前两条的一部分（假窗口跑真实重试逻辑 / 断言被拒文件不落盘），
> 但「用户双击 exe 时拖拽到底行不行」仍然只能人工验证——自动化环境里
> 根本起不来真正的 WebView2 窗口。

## 二、建议的下一步优化

### 高价值 · 建议优先做

> 上一轮列的 5 项（预设方案 / 可视化编辑器 / 结果面板 / 自定义 Logo / 同目录提示前置）
> **已在 v3.2.0 全部落地**，见「一、5」。

**1. 缩略图磁盘缓存**
现在每次进目录都要把几百张原图重新解码一遍出缩略图。可以按
`(路径, mtime, size)` 做 LRU 磁盘缓存（存到 `DATA_ROOT/cache/thumbs/`），
翻看大目录会明显更跟手。内存里的 EXIF 缓存已经有了，缩略图这块还缺。

**2. 用 `Image.draft()` 做 JPEG 解码期缩放**
这是**成本最低、收益最直接**的一条。Pillow 解码一张 6000×4000 的 JPEG 时，
如果最终只需要长边 1600，现在仍然是「全尺寸解码 → LANCZOS 缩放」。
而 `img.draft("RGB", (1600, 1600))` 能让 libjpeg 在 DCT 阶段就按 1/2、1/4、1/8
直接出小图，解码耗时能降到原来的 1/3~1/5，且对「长边限制」「缩略图」「预览」
这三种场景质量完全够用。改动量大概十几行。

**3. 大图优先调度（LPT）**
目前任务是按顺序投递给进程池，先到先得。如果前 6 张是 6000 万像素的大图、
最后一张是小图，总耗时会被最慢的那个进程拖长。改成**按预估像素数降序投递**
（Longest Processing Time first），makespan 会明显变短。改动量很小。

**4. exiftool 常驻模式（`-stay_open`）**
现在每张照片都要单独启动一次 `exiftool.exe`（每次约 50~150ms 的进程启动开销），
100 张就是 5~15 秒白等。exiftool 支持 `-stay_open True -@ -` 常驻 + 管道喂命令，
一次启动连续处理整批。这是纯 I/O 优化，和多进程互补，不冲突。

### 中等价值 · 有余力再做

**5. 自适应并发（按内存与磁盘类型）**
每张 6000 万像素的 RGBA 图约占 240MB，8 进程就是 2GB。可以按
「可用物理内存 ÷ 单张预估内存」动态下调进程数，避免在 8GB 机器上把系统
拖进交换分区（那样反而更慢）。同理，输出目录在机械盘上时，多进程并发写
会因寻道互相拖累，可以测一下写入速度再决定并发。

**6. RAW 格式支持**
通过 exiftool 读 CR2 / NEF / ARW / RAF 的 EXIF，用内嵌的 JPEG 预览图做处理与显示。
摄影用户刚需，但实现较复杂。

**7. 人脸 / 主体感知自动裁切**
裁切时优先保住人脸或画面主体，而不是无脑居中。
可用轻量人脸检测（OpenCV Haar 或 MediaPipe）先定位再决定裁切偏移。

**8. 右键菜单集成**
注册「用相机水印工具处理」到资源管理器右键菜单，
选一批图 → 右键 → 直接按上次配置处理。适合批量归档场景。

**9. 处理历史**
记录每次任务的参数与结果，支持「用同样的设置再跑一次」。

**10. 批量预读（readahead）**
worker 处理第 N 张时，主进程预读第 N+1 张进页缓存，隐藏磁盘延迟。
在机械盘上收益比较明显。

### 长期方向

**11. 视频水印**
短视频平台需求真实存在，但技术栈完全不同（需要 ffmpeg），
建议作为独立产品考虑。

**12. 更新机制**
本地工具，可选。如果分发量大，可以加一个「检查新版本」的轻量提示。

**13. 多语言**
界面文案抽成词条文件，加英文即可。

## 三、架构上的建议（给后续维护者）

1. **不要引入前端框架和 CDN**。现在纯 CSS + 原生 JS 的方案，
   离线稳定、体积小，也避开了之前那类编码陷阱。真要上框架，
   请把依赖本地化后一起打包。

2. **新增处理器要同时做三件事**，缺一不可：
   ① 在 `processor/filters|generators|mergers` 里注册；
   ② 在 `processor/schema.py` 里补上元数据（否则可视化编辑器里看不到、加不进来）；
   ③ 在 `build.spec` / `build_onedir.spec` 的 `hiddenimports` 里补模块名
   （否则打包后报 `Processor 'xxx' not found`）。
   测试 `test_features.py` 的 [B] 段会校验「已注册处理器都有元数据」。

3. **`config.ini` 不要放进打包资源**。它是用户可写文件，
   一旦打进 exe，开发机的调试配置就会污染新用户。

4. **任何调用外部 exe 的地方都要加 `CREATE_NO_WINDOW`**，
   否则窗口程序会闪黑框。

5. **⚠️ 打包版多进程必须调用 `multiprocessing.freeze_support()`**，
   且必须是 `if __name__ == "__main__":` 里的**第一句**。
   冻结环境下 spawn 子进程是「把 exe 再启动一遍」，不调用它的话每个子进程
   都会把整个桌面程序重跑一遍 —— 用户看到的是疯狂弹窗或直接卡死。
   **这个缺陷在源码模式下 100% 测不出来**，只有打包后才能暴露，
   所以 `test_features.py` 的 [H] 段专门做静态检查守着这条。

6. **多进程相关的东西一律要能退回串行**。多进程是加速手段，不是正确性前提。
   调度器要维护 pending 集合，池子挂了就把**没做完的**任务用串行补完。

7. **spawn 的子进程会把 `__main__` 重新导入一遍**。所以任何作为入口的脚本
   （包括临时调试用的启动器）都必须有 `if __name__ == "__main__":` 保护，
   否则子进程一导入就去抢端口、重开窗口。

8. **改完代码跑全套**：
   - 源码层：`selftest.py`（7 个模板 + EXIF）→ `smoke_test.py`（26 个接口）
     → `regress_samefolder.py`（同目录 / 拖拽 / 扫描排除）
     → `test_features.py`（预设、编辑器元数据、Logo、结果面板、深色模式、性能、打包安全）
   - 界面层：`ui_verify.py`（真实 Chromium 跑一遍并截图，含控制台报错检查）
   - 打包层：改了 `datas` / `hiddenimports` / 入口，两套 spec 都要重打，
     再用 `e2e_packaged_test.py` 验证**两种**产物。

9. **测试夹具不要依赖「批量删除」**。受管控环境（沙箱 / 企业策略 / 杀软）
   对单次批量删除有配额，一次性 `rmtree` 几十个文件会被整进程拦下，
   表现为「测试莫名其妙挂掉」。夹具改用「每次运行一个新目录」的写法，
   天然干净，也不需要删东西。

10. **两套 spec（onefile / onedir）要一起维护**。
    改了 `datas` / `hiddenimports` / 业务代码，两套都得重新打包，
    否则两种便携形态行为会不一致。
